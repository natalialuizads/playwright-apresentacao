Teste instável: caçar, entender, marcar

# caçar: repete até a falha aparecer e abre o trace dela

npx playwright test pix.spec.ts --repeat-each=30 --workers=4

 

# no CI: o que só passou no retry também quebra

npx playwright test --fail-on-flaky-tests

 

# de novo, só o que falhou

npx playwright test --last-failed

// a causa clássica: isVisible() não espera

expect(await status.isVisible()).toBe(true); // instável

await expect(status).toBeVisible(); // espera

 

test.fail(true, 'bug PIX-201: valor some no iOS');

test.fixme('Pix agendado: aguardando a funcionalidade');

1. Quase sempre é espera: isVisible, textContent ou count lidos na hora.

2. Ou é dado: dois testes mexendo no mesmo cliente.

3. Ou é ordem: um teste depende do que o outro deixou.

4. Retry esconde, não conserta. Instável é bug: tem dono e prazo.

Teste instável é o que passa e falha sem ninguém mudar nada. Primeiro, cace: --repeat-each roda o mesmo teste trinta vezes, em paralelo, até a falha aparecer, e o trace da repetição que falhou mostra o porquê. No CI, --fail-on-flaky-tests faz o teste que só passou no retry quebrar o pipeline, para o problema não ficar escondido. As causas mais comuns são três. Espera: isVisible, textContent ou count leem a tela na hora, sem esperar; troque pelo expect, que espera. Dado: dois testes usando o mesmo cliente. Ordem: um teste depende do que o anterior deixou. Enquanto não dá para consertar, marque: test.fail diz que o teste falha e sabemos por quê, e avisa se começar a passar; test.fixme pula o teste mas deixa registrado no relatório. O exemplo está no 26-instaveis.spec.ts.
