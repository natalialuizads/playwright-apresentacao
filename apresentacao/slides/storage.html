localStorage, sessionStorage e o que o login salva

// ler e escrever, sem page.evaluate

await page.localStorage.getItem('tatu.token');

await page.sessionStorage.setItem('msal.idtoken', 'x');

 

// guardar o sessionStorage (o storageState não guarda)

const itens = await page.sessionStorage.items();

 

// restaurar antes do app rodar, em todo teste

await context.addInitScript(({ itens, origem }) => {

  if (location.origin !== origem) return;

  for (const { name, value } of itens)

    sessionStorage.setItem(name, value);

}, { itens, origem });

O que o storageState() salva:

OndeSalva?
CookiesSim
localStorageSim
IndexedDBCom indexedDB: true
sessionStorageNão: guarde à parte

O sessionStorage é por aba e some quando ela fecha. Por isso fica de fora.

Exemplos em e2e/17-storage-e-abas.spec.ts.

O login reaproveitado depende do storageState, então vale saber o que ele leva. Cookies e localStorage, sim; IndexedDB, se você pedir com indexedDB true, que é onde Firebase e alguns SDKs guardam o token. O sessionStorage, não: ele é de uma aba só e some quando ela fecha. Desde as versões recentes, page.localStorage e page.sessionStorage leem e escrevem direto, sem page.evaluate. Quando o seu login vive no sessionStorage, como o MSAL do Azure AD por padrão, o caminho é ler os itens no setup, gravar num arquivo, e restaurar em todo teste com addInitScript, que roda antes de qualquer script do app.
