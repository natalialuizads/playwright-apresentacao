Ambientes · variáveis

Um config, vários ambientes

// playwright.config.ts

try { process.loadEnvFile(); } catch {} // lê o .env, se existir

 

const AMBIENTE = process.env.BASE_URL;

export default defineConfig({

  use: { baseURL: AMBIENTE ?? 'http://localhost:4200' },

  // com BASE_URL, o app já está no ar: não sobe nada

  webServer: AMBIENTE ? undefined : { command: 'npm start' },

});

 

// e2e/auth.setup.ts

await login.entrar(process.env.TATU_CPF, process.env.TATU_SENHA);

Quem ganha: o terminal, o CI e o Docker ganham do .env.

.env fora do git; o .env.exemplo documenta cada variável.

No CI: os segredos vêm do cofre da ferramenta.

Java: System.getenv("TATU_BASE_URL"); opções do Maven com -D.

BASE_URL=https://homologacao.exemplo \

  npx playwright test

O config é código, então lê variáveis de ambiente como qualquer programa Node. O process.loadEnvFile, nativo do Node 20.12 em diante, lê o .env da pasta sem instalar nada; se a mesma variável já existir no terminal, no CI ou no Docker, ela ganha do arquivo, o que conferimos no projeto. A BASE_URL troca o alvo: sem ela, o webServer sobe o app local; com ela, a suíte roda contra homologação ou um container, e nada é iniciado. Credenciais nunca ficam no código: o setup lê TATU_CPF e TATU_SENHA. O .env fica fora do git e o .env.exemplo documenta tudo. No Java, System.getenv lê o ambiente, e as opções do Maven chegam com -D, como o -Dcanal e o -Dheaded.
