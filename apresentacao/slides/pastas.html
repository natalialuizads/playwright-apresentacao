1. Por funcionalidade, não por tipo: pix/ junto, não "testes-de-formulario".

2. Page Object para tela usada por vários specs; component para pedaço que se repete.

3. Fixtures num lugar só, uma por assunto, juntas com mergeTests.

4. Dados em fábricas, não em JSON copiado de teste em teste.

5. Configs na raiz: base, CI e local herdando uma da outra.

A regra principal: organize por funcionalidade do produto, como o próprio app. Quem mexe no Pix encontra os testes do Pix numa pasta só. Page Objects ficam numa pasta própria e só existem para telas usadas por vários testes; pedaços que se repetem em várias telas, como o menu ou o cartão de saldo, viram components. As fixtures ficam juntas, uma por assunto, e o index junta todas com mergeTests, então o spec importa test de um lugar só. Dados de teste vêm de fábricas, funções que criam um cliente ou um Pix com valores padrão, e não de JSON copiado. Os arquivos de config ficam na raiz. No projeto de exemplo os specs são numerados porque seguem a apresentação; o README mostra esta estrutura para uma suíte de produto.
